# Native PY_SPF 1.3 — 통신 확인과 로그

통신 확인은 **View → Communication Monitor**에서 연다. 기존 NI 화면 형식의 별도 창이며, 장치 조작 화면의 비활성화와 별개로 로그를 확인하는 용도다. 현재 앱 세션의 로컬 진단 파일을 읽으며 장치 소켓을 열거나 명령·상태 조회를 보내지 않는다.

## 화면에서 확인하는 내용

- 로그에 저장된 연결·제어 준비 상태와 최근 통신·STATUS 응답의 경과 시간.
- TX/RX, 조회 재시도·timeout, 쓰기 ACK timeout 등 통신 카운터.
- 대기 명령 수와 Reset/Fault 중복 요청 억제 등 큐 처리 정보.
- 시간·종류·내용을 포함한 최근 이벤트. **Problems only / Show all**로 표시 범위를 선택한다.
- 로그 파일 읽기·기록 이상과 데이터 갱신 상태.

**Pause display**는 이 창의 표시 갱신만 멈춘다. 장치 통신·원래 화면·로그 기록은 계속 진행한다. 다시 표시할 때는 보관 중인 최근 기록을 사용하므로 일시정지 동안의 모든 이력을 무제한 보존하는 기능은 아니다.

**Clear display**는 표시 중인 행만 지우고 저장된 로그를 삭제하지 않는다. **Copy displayed**는 현재 보이는 이벤트를 복사하며, **Open log folder**는 이 세션의 폴더를 연다. 이 버튼들은 장치 명령을 보내지 않는다.

표시된 연결 상태는 마지막 로그 표본의 값이다. 로그가 오래됐거나 읽기에 실패하면 현재 장비 상태를 확정할 수 없으며, 이를 장비 통신 단절과 구분해 확인해야 한다. 진단 파일을 읽을 수 없다는 사실만으로 장치가 OFF라고 판정하지 않는다.

| 표시 | 해석 |
|---|---|
| `LOG: LIVE` | 최근 heartbeat를 읽었고 보고된 기록 오류·누락이 없는 상태. |
| `LOG: DEGRADED` | 표본은 있으나 기록 오류 또는 이벤트 누락이 보고됨. |
| `LOG: STALE`, `WAITING`, `READ_ERROR` | 표본이 오래됐거나 없거나 읽기에 실패함. 기본 heartbeat 신선도 기준은 3초이며 장비 현재 상태는 `UNKNOWN`으로 표시함. |
| `DEVICE (saved): READY` | 신선한 표본이 연결·제어 준비 및 최근 응답을 보고함. |
| `DEVICE (saved): NO RECENT REPLY` | 파일 표본은 신선하지만 마지막 장비 응답이 기본 10초를 넘음. |
| `DISCONNECTED`, `INITIALIZING`, `STOPPED` | 마지막 표본에 기록된 장치 미연결·준비 중·앱 정지 상태. |

패널의 3초·10초는 표시 판단 기준이다. 컨트롤러가 STATUS 경과 시간에 따라 장치 제어를 비활성화하는 기존 정책을 바꾸지 않는다.

## 저장 위치와 형식

Windows 설치형·Portable EXE는 실행마다 다음 경로에 별도 세션 폴더를 만든다.

```text
%LOCALAPPDATA%\PY_SPF_1.0\logs\<UTC 시각>_<세션 식별자>\
```

1.3으로 업데이트해도 사용자 데이터의 `PY_SPF_1.0` 경로는 유지한다. 소스의 `run_native.bat` 기본 위치는 저장소의 `logs/native/`이며 `--diagnostics-dir`로 바꿀 수 있다. Python으로 직접 실행하면 이 옵션을 지정한 경우 진단을 기록한다.

| 파일 | 형식과 내용 |
|---|---|
| `events.jsonl` 및 회전 파일 | UTF-8 JSON Lines. 한 줄에 이벤트 하나를 저장한다. UTC·단조 시각·종류·내용을 포함하며 새 형식에는 세션·순번과 큐 요청 식별 정보를 추가한다. |
| `heartbeat.json` | 최근 진행·연결·통신·큐·기록 상태의 JSON 표본. 기본 약 1초마다 같은 파일을 갱신한다. |
| `stacks.txt` | 메인 루프 진행 지연이 10초 이상일 때의 Python 스택. 당시 실행 위치의 근거이며 원인 확정 판정은 아니다. |
| `stdout.log`, `stderr.log`, `launcher.json` | EXE 실행기의 출력·오류·시작 정보. 컨트롤러 이벤트 파일과 구분한다. |

이 기록은 별도 **Programmer → Data Logging**의 `datalog.csv`와 다르다. 기존 CSV는 선택적으로 전류·LBO 온도 등을 저장하는 기능이며, 통신 이벤트·오류 이력의 저장소로 사용하지 않는다.

이벤트 파일은 기본 **16 MiB**에서 회전한다. `events.jsonl`과 최신 순서의 `events.1.jsonl`, `events.2.jsonl`, `events.3.jsonl`까지 **총 4개**를 보관하므로 이벤트 보관량은 세션당 약 64 MiB다. 한 이벤트는 나누지 않으므로 파일 하나가 제한을 조금 넘을 수 있다. 이 한도는 이벤트 파일에 적용하며 다른 진단·실행기 파일과 여러 세션을 합한 전체 디스크 사용량의 한도는 아니다.

## 기록과 표시의 제한

진단은 제어를 막지 않는 범위에서 기록한다. 기본 대기열은 **4096건**이며 쓰기 실패 시 재시도할 한 건을 별도로 보관한다. 대기열이 가득 차면 새 진단 이벤트를 버리고 누락 수를 남기며, 쓰기 실패는 기록 상태에 표시하고 이후 다시 시도한다. `seq`의 공백과 `heartbeat.json`의 `logger.dropped_events`는 기록 누락을 확인하는 근거다. 로그 파일은 크기 제한에 도달하면 회전하며 보관 한도를 지난 오래된 이벤트는 남지 않는다.

쓰기 작업은 기본 약 **0.25초**마다 진행하며 한 번에 **128건·20 ms**를 처리 기준으로 사용한다. heartbeat의 `logger`에는 대기 건수·최고 대기 건수·기록/누락 수·회전 수·파일 오류와 실패 횟수를 남긴다. 이 간격과 시간 기준은 느린 파일 시스템 호출의 완료 시간을 보장하는 값은 아니다.

통신 확인 창은 처음에 이벤트 파일 끝의 최대 **256 KiB**를 읽고, 이후 기본 **0.25초** 간격으로 변경분을 제한해서 읽는다. 최근 이벤트는 최대 **1000건**을 보관하며 한 화면에는 그중 최대 **300건·48000자**를 표시한다. 파일 끝의 미완성 줄은 다음 갱신까지 기다리며, 파일 회전·일시 누락·잘못된 줄 때문에 장치 제어를 멈추지 않는다. 읽기와 화면 반영을 분리하고, NI 화면 조작은 UI 스레드에서만 수행한다.

따라서 디스크 부족·권한 문제·매우 느린 저장장치에서는 기록이 지연되거나 누락될 수 있다. 이 경우 패널의 마지막 표본을 현재 상태로 간주하지 않는다. 세션 내부 파일 보관 한도와 실행마다 생성하는 세션 폴더의 누적은 별개이므로, 장기간 보존할 자료를 따로 복사하고 오래된 종료 세션은 사용자가 정리한다.

## Reset/Fault 중복 제한

전체 Fault Reset은 아래 **14건**이 모두 끝날 때까지 한 묶음만 유지한다. 대기 중·송신 중·응답 대기 중에 같은 Reset을 다시 눌러도 새 묶음을 추가하지 않는다.

```text
2044 → 2049 → 2052 → 2050
  → 1089 → 1088 → 1014 → 1066 → 1057
  → 1089 → 1088 → 1014 → 1066 → 1057
```

앞의 네 건은 기존 Reset 쓰기이며 뒤의 다섯 가지 Fault 조회를 두 번 수행하는 원래 순서를 유지한다. 별도 **BWD Reset은 2018 → 1066**의 독립된 한 묶음으로 제한한다.

Fault 조회 갱신만 반복한 경우에는 같은 쓰기 구간의 기존 확인 조회와 합친다. 사이에 장치 쓰기가 하나라도 들어오면 그 쓰기 뒤의 새 조회는 유지하므로, 쓰기 전 표본으로 쓰기 후 확인을 대신하지 않는다.

각 요청이 timeout이면 그 항목을 종료하고 남은 순서를 진행한다. 마지막 항목까지 완료·timeout·취소로 끝나면 같은 작업을 다시 요청할 수 있다. 재연결·프로그램 종료·큐 초기화 때도 묶음 제한 상태를 해제한다. 억제된 요청과 완료·timeout·취소는 구조화된 `QUEUE` 이벤트와 카운터에서 확인할 수 있다. 중복 억제 횟수는 통신 실패 횟수가 아니다.

이전 실사용 로그에서는 반복 Fault Reset으로 STATUS 조회가 밀려 제어 화면이 잠시 비활성화된 사례가 확인됐다. 중복 제한은 이 누적을 줄인다. 일반 명령 전체에 대한 우선순위나 STATUS 조회의 최대 간격을 보장하는 정책은 이번 변경의 범위가 아니다.
