원본 XP Spitfire 통신 관찰 결과 — 격리 시뮬레이터 시험

이 문서의 시각은 모두 호스트 기록을 KST로 표시한 2026-11-01 시각이다.
패킷 수신 시각과 GUI 동작 시각을 구분했다. 동작 구간은 호스트의 명령 발행부터
완료 파일 수신까지의 범위이며, 그 안의 패킷 모두가 해당 클릭 때문에 발생했다는 뜻은 아니다.

1. 실제 수집량과 출처

01:42:42.692–02:16:31.892에 원본 XP의 UDP 요청 20,148개와 합성 응답 20,148개를 기록했다.
이 중 조회는 20,134개/64개 태그이고, 변경 명령은 14개/2개 태그이다.
원본 송신은 10.19.70.2:1024 → 10.19.70.13:1024, 응답은 반대 방향이다.
요청 형식: Spectra-Physics:CMD_ECLIPSE,[1068]EMPOPTOUT?\n
응답 형식: Spectra-Physics:REPLY_ECLIPSE:<1068>1\n

프로세스 실행·경로·해시·게스트 보조 코드의 UDP 미생성 증거로 원본 출처를 교차 확인했다.
원본 EXE SHA256: 8a87bcad1709f93358cba5f5588647999524ba8b481c2f38cc6cc82a96623e9b
패킷 자체에는 Windows PID가 없으므로 프로세스 귀속은 이 별도 증거와 함께 해석해야 한다.
classic .pcap은 tcpdump와 dpkt로 읽었다. 46,666개 프레임 전체를 읽었고,
시험 UDP의 양방향 주소·포트·페이로드를 로그와 대조한 결과 누락/초과는 각각 0개였다.
이 검증 범위를 넘어선 손실이나 실물 장비 동작까지 증명하는 것은 아니다.

2. Opt-out 전환과 변경 명령

01:51:44.846–01:51:47.601에 [2036]EMPOPTOUT 1이 6회, EMPOPTOUT 0이 5회 발생했다.
사용자가 해당 시간대에 직접 여러 번 눌렀다고 “직접 눌렀음”으로 확인했다.
최초 ON 요청은 UDP 순번 9479이며, 이때 시뮬레이터 RAM만 0→1로 바뀌었다.
이후 ON 5회는 1을 유지했고, OFF 5회는 모두 거부하여 시뮬레이터는 OFF로 바뀌지 않았다.

자동화 action8은 한 번 입력을 시도했으나 ON 확인에 실패했다(exit57).
그 동작의 호스트 구간에는 2036 요청이 없었다. action11은 이미 ON임을 읽고 입력을 생략했다.
따라서 실제 전환을 자동 클릭의 성공으로 보고하지 않는다. 수정한 자동 ON 클릭 경로의
OFF→ON 성공은 이번 실행에서 확인되지 않았다.

1068 EMPOPTOUT? 응답은 총 3회였다:
  01:42:52.437 = 0 / 01:58:25.283 = 1 / 02:09:40.788 = 1
1068은 이 기록에서 반복 폴링되지 않았으며, 시작·재시작·재접속 초기화 때 관찰됐다.

원본이 자동으로 보낸 [2047]EMP:LBOBREAK 1은 다음 시각에 각 1회였다:
  01:42:56.155 / 01:58:27.086 / 02:09:43.868
세 요청 모두 거부했다. 전체 거부 명령은 OFF 5회와 2047 3회를 합친 8회이다.
2036/2047에는 원본 스케줄러를 진행시키기 위한 같은 태그의 합성 ACK0를 보냈다.
ACK0를 장비 설정 성공으로 해석하면 안 된다. 원본 x86 디코더 검증에서도
<2036>0 자체는 Opt-out을 토글하거나 새 명령을 생성하지 않았다.

3. 반복 조회와 관찰 간격

1039 TDG:STBH?가 10,258회로 가장 많았다. 그 사이에 다음 기본 조회가 반복됐다:
  HED:STB?, TDG:STB?, EMP:STB?, ECU:STB?, EMP:READ:DIODE:CURR?,
  EMP:READ:POW?, ECU:STBH?, ECU:READTEMP?, TDG:READ:OSCQUEST?, ECU:HUM?,
  TDG:HV:ON?, EMP:LBOTEMP?, ECU:TECTEMP?, STATUS?
서비스 화면에서는 HV2CURR?(1056), HV1CURR?(1055), HV1VOLT?(1042), HV2VOLT?(1043)가
추가되어 각각 433회 관찰됐다. 이는 전류·전압 조회이며 HV ON 명령을 실행한 것이 아니다.
Opt-out ON 이후에도 EMP:STB?, 전류·출력·LBO 온도 조회가 계속됐다.
1000 *idn?는 초기 구간 6회, 프로그램 재시작 구간 6회, 경고 후 재접속 구간 3회였다.

아래 경계는 실제 패킷 순번·서비스 조회의 첫 출현·수동 입력 구간으로 정했다.
표의 간격은 같은 조회가 다시 수신될 때까지의 중앙값(초)이다.

Opt-out이 폴링을 늦춘다는 인과관계나 실물 컨트롤러의 고정 주기를 뜻하지 않는다.
세부 횟수와 최소/최대 간격은 protocol-period-statistics.json에 있다.

4. 화면 동작과 중단·복구

ON 확인 후 action13–17에서 Temperature Control, Timing and High Voltage,
Active Faults, Empower Setup, About/Help를 열어 해당 창이 나타남을 확인했다.
이들 동작의 전체 호스트 구간은 01:53:25.324–01:57:48.547이다.
이 구간에는 변경 명령 없이 반복 조회만 관찰됐다. 개별 동작 경계는 summary.json에 있다.
action18은 File→Exit로 원본 프로세스 종료를 확인했고, action19는 원본 EXE를 재시작했다.

01:59:15.205 이후 요청이 멈췄고 원본의 “Remote system not responding” 경고가 관찰됐다.
02:09:35.629부터 다시 요청이 기록됐다. 이 620.424초 공백에는 점검, 시뮬레이터 중지·재개,
그리고 검토한 경고 OK의 재시도(action23)가 포함된다. 최초 중단 원인은 확정하지 못했다.
기존 서버가 비정상 종료했거나 UDP 스레드가 죽었다고 단정할 증거는 없다.

복구 후 통신은 정상적으로 기록됐지만 메뉴는 비활성화되어 action24의 창 열기는
차단됐다(exit43, 항목 클릭 없음). regensvc 재진입(action25)도 메뉴를 복구하지 않았다.
정적 분석상 원본은 경고 때 메뉴를 비활성화하면서 curtain_not_open을 다시 설정하지 않고,
1085 응답은 이 플래그가 이미 0이면 메뉴를 다시 활성화하지 않는다.
이는 관찰 현상과 일치하는 원본 GUI 논리 문제이며, 실물 장비의 응답 결함을 뜻하지 않는다.

마지막 action27은 메뉴 진입 차단 후, 확인한 원본 메인 창에 SC_CLOSE를 한 번 보냈다.
CVI의 close_ctrl=2→QuitProgram→QuitUserInterface 경로를 확인했으며,
동작 결과에서도 해당 원본 프로세스가 종료됐음을 확인했다.
종료 동작의 호스트 구간은 02:16:14.872–02:16:46.060이다.
이 구간을 정확한 닫기 클릭 시각으로 오해해서는 안 된다.

5. 시계와 해석 범위

게스트 시계와 호스트 시계의 차이가 실행 도중 달라졌다. 발행·업로드로 계산한 인과적 범위는
초반(action1–19) 호스트−게스트 약 +102.087~+105.460초,
후반(action20–27) 약 −1.587~+3.632초이다. 이는 지연을 포함한 범위이지 정밀 동기화 값이 아니다.
전체 실행에 하나의 시차를 적용할 수 없다. 게스트 시계는 변경하지 않았고,
패킷과 화면 이벤트를 게스트 시각으로 직접 맞추지 않았다.

모든 응답은 시뮬레이터 값이다. 실제 응답 예도 *idn?="Spectra-Physics, SPF_XP_LOG_AUDIT, 0, 1.6.0",
EMP:READ:DIODE:CURR?=5.50, EMP:READ:POW?=1.25, EMP:STB?=1,
STATUS?=0, TDG:STBH?=0처럼 고정된 시험 데이터였다.
이 숫자를 실제 출력·전류·발진·고전압 상태로 해석하지 않는다.
이번 실행은 원본 EXE의 송신 형식·조회 순서·사용자 입력에 따른 요청·GUI 동작을 확인했다.
실물 컨트롤러의 Opt-out 의미, 응답 지연, 장비 상태 전이, fault/interlock 및 실제 측정치는 미확인이다.
원본 실물 제어 PC와 레이저는 시험 대상이 아니었다.
