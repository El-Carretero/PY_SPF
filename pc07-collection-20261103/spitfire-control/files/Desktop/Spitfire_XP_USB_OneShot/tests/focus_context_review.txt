Confirmed original application facts
- MainCallBack at 0x0040b6c4 handles event 7 (keypress), recognizes access strings,
  calls SetAccessLevel, and returns zero. Recognition does not consume the key.
- SetAccessLevel cases 0 and 1 consist of GUI attribute/visibility operations.
  This alone does not prove that sending those characters to a window is safe:
  the CVI runtime may also route an unconsumed character to a virtual control.
- Win32 hwndFocus == main window is insufficient to identify that virtual
  control because CVI draws multiple interactive controls inside the same HWND.

physical hardware. Actual ring-letter selection remains unproved and excluded.

Read-only runtime lookup corroboration
Locked cvirte.dll SHA256:
d4151c53a2ecee4431ba88cd90d88db575f8ad18a6e48484501ff10a83c0db6d
Preferred image base 0x68420000; addresses below refer to that base.
- GetActiveCtrl export 0x6855bff1 calls 0x68559ce5.
- 0x68559ce5 resolves the application panel and calls 0x68558926.
- 0x68558926 reads the native panel handle at [panel_object]+0xa0 and calls
  0x6843ef92. The result is mapped back to an application control object/ID.
- 0x6843ef92 initializes result zero, checks [native_object]+0x44, obtains the
  holder at +0x54, and passes [holder] to 0x6844258b.
- 0x6844258b interprets node+8: type1 uses node+12 through 0x6843d705; type3
  returns node+12+1. Other paths can leave the zero result.
- SetActiveCtrl is NOT a read-only alternative: export 0x6855c3b9 calls
  0x6855c035 -> 0x68559c3e -> native focus operation 0x6843efbc.

Required implementation boundary
Validate native lookup against the isolated XP process before using it as a
guard. Check virtual focus before any foreground/focus change, menu click, access
typing or auxiliary close, and after any transition that can change that focus.
Do not clear an unsafe focus using SetFocus/SetActiveCtrl/Tab/Escape because the
clearing action itself can trigger a pending edit or another original callback.
Without a proven read-only focus/dirty context, block the affected UI operations
and preserve passive capture. A warning to the user is not a replacement guard.

Final production addendum
Reviewed executable SHA256:
3286d8e3256d8abb23f39acff32adaa9ebef26476e36756b031bb9d8fe25c56c

1. All keyboard generation and regensvc/user helper routes were removed. The
   five-screen plan preserves the initial access mode. User-mode Empower Setup
   under Opt-out ON is explicitly skipped before input.
2. The XP read-only bridge evidence in
   ../validation/evidence/focus-bridge01/cvi-focus.jsonl and cvi-focus-map.jsonl
   corroborates platform window -> generic panel -> public CVI wrapper binding.
   Main selection value 1 translates to native ID 2 and then public control 3
   (Motor Speed); it is not interpreted directly as public control 1 or 2.
3. The production guard permits only a verified main no-control context or its
   closed Motor Speed ring context for fixed MENU mouse navigation. It never
   clicks the ring or sends characters to it. Remembered numeric
   or unknown main controls remain blocked even when the active flag is zero.
   Existing auxiliary windows, original popups, edit children/caret, changed
   access mode, warnings or unreadable identity/context stop automatic input.
4. Full static dirty-numeric commit evidence is in cvi_hidden_edit_review.json.
   HidePanel dispatches cleanup event 0x23. A text dirty bit becomes flag0x40;
   the numeric handler parses/updates the value and returns0x300008, which the
   translator maps to application EVENT_COMMIT. Normal teardown then clears
   generic panel fields +0x44 and +0x48. A remembered selector alone is not a
   pending edit. The examined clean DisplayPanel initialization path does not
   set the text dirty latch; this is not a claim about arbitrary widget types.
5. Before foreground activation and again before selecting a menu item, the
   exact hidden target is bound through its window/generic/wrapper identities
   to the original panel-global ID and both +0x44/+0x48 must be zero. The shown
   HWND must match this checked target. No values or keys are entered.
6. LastInputInfo and held-input checks run before foreground changes/mouse-down.
   Automatic HidePanel dispatch is limited to that checked, newly shown target,
   with no intervening input since the runner's own menu-item mouse-up. This
   uses target context evidence as well as input history; input history alone
   is not treated as proof that a previously hidden panel was clean.
7. Helpers use the Windows GUI subsystem to avoid creating foreground consoles.
8. The final revision changes only proof-file reading: a bounded snapshot opens
   with READ/WRITE/DELETE sharing and closes before evidence I/O/parsing. The
   seven-key validation and five-second freshness limit remain unchanged, as
   does the context/focus policy above. XP-compatible imports were verified.
